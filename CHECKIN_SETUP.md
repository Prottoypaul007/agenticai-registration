# Registration email and workshop check-in

1. Make sure `supabase/migrations/006_email_and_checkin.sql` has been applied after migration 005. The new workflow also needs `007_manual_review_and_qr_delivery.sql`. On a live site, deploy the updated app before applying 007 so the old registration handler cannot issue QR emails during the rollout.
2. In [Google Cloud Console](https://console.cloud.google.com/), create or select a project and enable the **Gmail API**. Under **Google Auth Platform**, configure the OAuth consent screen for your Google Workspace organization (Internal). Create a **Web application** OAuth client and add `https://developers.google.com/oauthplayground` as an authorized redirect URI.
3. Open the [Google OAuth 2.0 Playground](https://developers.google.com/oauthplayground/). In its settings, select **Use your own OAuth credentials** and enter that client ID and secret. Request only `https://www.googleapis.com/auth/gmail.send`, authorize while signed in as the Workspace sender mailbox, and exchange the code for tokens. Copy the **refresh token**. Offline access is required so the server can send after a participant registers without someone signing in each time.
4. Set `GMAIL_SENDER_EMAIL`, `GOOGLE_OAUTH_CLIENT_ID`, `GOOGLE_OAUTH_CLIENT_SECRET`, and `GOOGLE_OAUTH_REFRESH_TOKEN` in `.env.local` and in the production server environment. `GMAIL_SENDER_EMAIL` should be that Workspace mailbox, such as `no-reply@your-domain.com`, or a verified Gmail send-as alias for it. Never place the client secret or refresh token in a `NEXT_PUBLIC_` variable or commit them.
5. Set `CHECKIN_SIGNING_SECRET` to a long random value (at least 32 characters) in both environments. Keep it stable: changing it invalidates tickets already emailed. The local `.env.local` has been given a generated secret if it lacked one. Never expose this value to the browser or commit it.
6. Deploy the updated app, then apply `supabase/migrations/007_manual_review_and_qr_delivery.sql` in the Supabase SQL Editor. Migration 007 adds the payment review queue, cancellation reasons, delivery timestamps, and the admin-only QR issue action. Then make a test registration with an email address you can access. Registration saves the submitted transaction ID and shows a pending review message. It does not email or show a QR yet.
7. In `/admin` -> **Payment review**, find the registration under **Awaiting review**. Compare its transaction ID, method, amount, and destination against the real payment account. Click **Verify payment & send QR** only after confirming the payment. The email contains the participant's name, institution, attendance choice, reference, and an embedded/attached QR code. The QR does not include payment or bank data. If the transaction cannot be matched or criteria are not met, select a cancellation reason and send the polite notice. Sent and rejected registrations remain in separate review views, with timestamps and reasons in participant details and CSV export. Failed emails can be retried.
8. On October 17 or 18, 2026 (Bangladesh time), open `/admin` -> **Check-in** and scan the QR with a phone or laptop camera. The site uses the current workshop day automatically. Camera scanning on a phone requires HTTPS. A handheld scanner can paste the QR content into the text field.

Check-in requires a valid signed QR that an admin sent after review, an allowlisted admin, and attendance for that day. The scan records attendance; it does not verify a payment transaction. A repeat scan shows the original time without creating another check-in. Participant details and the CSV export show QR delivery, cancellation reasons, and both check-in timestamps. If Gmail API is unavailable, the registration stays saved, QR delivery is marked `failed`, and an admin can retry it.

If migration 007 is not applied, the admin review actions cannot run. If the Gmail API variables are missing, the Workspace mailbox is not authorized, or the refresh token is revoked, registrations still save, but email delivery fails until fixed and retried.
