# Registration email and workshop check-in

1. Apply `supabase/migrations/006_email_and_checkin.sql` in the Supabase SQL Editor after migration 005. It adds email status, separate Day 1 and Day 2 attendance timestamps, and an atomic admin check-in function. If you ran an earlier version of migration 006, run it again to replace the check-in function with the attendance-only rule.
2. In [Google Cloud Console](https://console.cloud.google.com/), create or select a project and enable the **Gmail API**. Under **Google Auth Platform**, configure the OAuth consent screen for your Google Workspace organization (Internal). Create a **Web application** OAuth client and add `https://developers.google.com/oauthplayground` as an authorized redirect URI.
3. Open the [Google OAuth 2.0 Playground](https://developers.google.com/oauthplayground/). In its settings, select **Use your own OAuth credentials** and enter that client ID and secret. Request only `https://www.googleapis.com/auth/gmail.send`, authorize while signed in as the Workspace sender mailbox, and exchange the code for tokens. Copy the **refresh token**. Offline access is required so the server can send after a participant registers without someone signing in each time.
4. Set `GMAIL_SENDER_EMAIL`, `GOOGLE_OAUTH_CLIENT_ID`, `GOOGLE_OAUTH_CLIENT_SECRET`, and `GOOGLE_OAUTH_REFRESH_TOKEN` in `.env.local` and in the production server environment. `GMAIL_SENDER_EMAIL` should be that Workspace mailbox, such as `no-reply@your-domain.com`, or a verified Gmail send-as alias for it. Never place the client secret or refresh token in a `NEXT_PUBLIC_` variable or commit them.
5. Set `CHECKIN_SIGNING_SECRET` to a long random value (at least 32 characters) in both environments. Keep it stable: changing it invalidates tickets already emailed. The local `.env.local` has been given a generated secret if it lacked one. Never expose this value to the browser or commit it.
6. Deploy, then make a test registration with an email address you can access. The email contains the participant's name, institution, attendance choice, reference, and an embedded/attached QR code. The success page also offers a QR download. The QR does not include payment or bank data.
7. On October 17 or 18, 2026 (Bangladesh time), open `/admin` -> **Check-in** and scan the QR with a phone or laptop camera. The site uses the current workshop day automatically. Camera scanning on a phone requires HTTPS. A handheld scanner can paste the QR content into the text field. Review payment manually in the participant record as a separate task.

Check-in requires a valid signed QR, an allowlisted admin, a registration that has not been rejected, and attendance for that day. Payment and approval status do not affect attendance check-in. A repeat scan shows the original time without creating another check-in. Participant details and the CSV export show email delivery and both check-in timestamps. An admin can retry a failed email from the participant details. A successful registration is kept even if Gmail API is unavailable; its email status becomes `failed` and the participant can download the QR on the success page.

If migration 006 is not applied, email delivery and check-in cannot be completed. If the Gmail API variables are missing, the Workspace mailbox is not authorized, or the refresh token is revoked, registrations still save, but email delivery fails until fixed and retried.
